# v1.9 之后的工程开销检查

2026-10-27，用户要求停止更深主干对战，转向工程分析。对战已停止，保留 9 局完整结果（更深候选 0 胜 4 平 5 负）；默认仍为 v1.9。本次只做隔离微基准，没有替换生产规则、搜索或默认模型。

## 浏览器执行位置

内置 AI 由 `src/App.tsx` 维护常驻 Web Worker，`src/game/ai.worker.ts` 加载 Wasm 后执行搜索，完成后将结果发回界面。正常完成的对局步骤会保留 Worker 和搜索缓存；取消未完成搜索时才终止 Worker。界面也初始化自己的 Wasm 实例，供轻量规则接口使用。

这套结构适合当前离线可用的小模型和单机对弈。当前编译带 `-O3 -msimd128`，搜索仍是单线程，启用 SIMD 编译不等于整个推理都已向量化。浏览器执行本身不是此次更深主干退步的解释：模型对照使用的是原生 C++ 动态库。是否需要远端计算应由目标设备上的响应、功耗与运维需求决定。

## 合法点和翻子：已做隔离微基准

当前 `cpp/othello.hpp` 使用两个 uint64 位棋盘。合法点按八个方向固定六次传播，已经避免逐格枚举。翻子沿每条方向射线循环，直到遇到非对方棋子。

独立候选实现见 `benchmarks/movegen.cpp`：合法点用 1、2、4 距离的倍增前缀传播；翻子分别试同类传播，以及预计算 64×8 射线表、查找最近非对手棋子的位扫描。射线表是 4 KiB，只保存棋盘几何，不按整盘局面建表。位传播思路也见 [Edax 的主作者源码](https://github.com/abulmo/edax-reversi/blob/master/src/board.c)；这里的测试实现独立编写，没有复制其代码。

正确性对照覆盖 8,192 个可达局面的全部 64 个翻子落点及 100,000 个随机不重叠位棋盘。每轮测 9,830,400 次调用，共 5 轮，重复之间加入编译器屏障，取中位数。原始数据、编译参数和来源哈希见 [微基准数据](benchmarks/movegen-2026-10-27.json)。

| 局部算法 | 原生提速 | Wasm 提速 |
| --- | ---: | ---: |
| 合法点：倍增位传播 | 1.72× | 1.26× |
| 翻子：倍增位传播 | 1.84× | 3.80× |
| 翻子：射线表＋位扫描 | 3.08× | 4.50× |

Wasm 在 Node 中运行，并非浏览器实测。这些是函数微基准倍率，不代表整局、搜索或棋力提升；原生与 Wasm 的运行环境不同，表中只比较各自内部的新旧实现。

## 代码中其他可减少的重复工作

1. **合并策略／价值推理。** MCTS 扩展同一叶节点时分别调用 `policy(p)` 和 `evaluate(p)`，两者各自刷新共享特征；更深版本还各算一遍残差块。提供共享中间激活的一次双头推理接口，可保持模型和选择语义。
2. **复用合法落点。** MCTS 已算 `legal(p)`，`Network::policy(p)` 内又计算同一集合。可将掩码传入内部推理接口。对强制 pass 也可避免重复规则检查。
3. **复用翻转掩码。** `play()` 内计算翻子；`ot_play()` 为返回翻子数量又算一遍。前端动画的 `flips()` 还会调用合法性和完整落子。可让一次落子同时返回新局面、翻转掩码与数量，供后续使用。前端调用量低，搜索热路径的复用优先级更高。
4. **减少搜索热循环的管理开销。** 检查树节点／边分配、子树搬移和计时调用的占比，再考虑保留容量、紧凑存储或有界批次查时钟。批量计时需要验证时限误差，不能只看节点数。

建议先做共享双头推理与规则热点优化。每项先验证结果一致，再测固定工作量和真实浏览器耗时；搜索对战保持停止，除非用户重新要求。

## 微基准复现

```sh
mkdir -p .build/engineering
clang++ -std=c++17 -O3 -I cpp benchmarks/movegen.cpp -o .build/engineering/movegen-bench
.build/engineering/movegen-bench
EM_CACHE="$PWD/.build/em-cache" em++ -std=c++17 -O3 -msimd128 -I cpp benchmarks/movegen.cpp \
  -sENVIRONMENT=node -sSINGLE_FILE=1 -sEXIT_RUNTIME=1 -o .build/engineering/movegen-bench.cjs
node .build/engineering/movegen-bench.cjs
```

## 后续接入与验证

用户随后要求先落地这两项，再重跑深模型 vs v1.9。优化已接入 C++ 热路径：MCTS 调用一次双头推理并传入已算合法掩码；残差激活只执行一次；合法点使用倍增前缀传播，翻子使用 4 KiB 射线表。落子接口复用翻转掩码计数，新 `ot_play_with_flips` 直接返回翻子列表，前端接口支持该导出并兼容旧 Wasm。

验证两份模型各 1,026 局面（含终局），评分与策略概率逐项误差为零；各 24 个冷根、20 个连续子树复用局面，固定 512 次模拟时走法、评分、根访问、选步和树统计完全一致（计时除外）。优化 Wasm 与原版在 1,205 步规则转换及 6 次 pass 中保持合法点、估值、棋盘和翻子列表一致。原生规则／残局、ASan／UBSan、14 项网页测试和前端构建通过。

相同 12 局面、每局面 512 次模拟的独立搜索短测，深模型耗时中位数由 0.17493 秒降至 0.10938 秒，约 1.60×；v1.9 为 0.04742→0.04703 秒，本组收益约 0.8%，接近计时噪声，不能宣称明显加速。数据见 `models/engineering-rerun1-search-benchmark.json`。模型权重与选择语义未改动。

对比重跑时，两份模型都使用同一个优化库，以避免工程实现不一致影响公平性。生产冻结 v1.9 的历史源码／Wasm 继续由原归档核对；本轮优化库和优化 Wasm 使用隔离构建，工程快照与校验记录见 `models/engineering-rerun1.json`。这不提升深模型为默认。
